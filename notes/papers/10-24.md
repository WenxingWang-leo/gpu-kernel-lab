## 一句话总结

合并与否只看一条：同一条访存指令里，warp 的 32 个 lane 地址是否落在同一段连续且对齐的区间。是就合成一次事务。不是就拆成多次。`threadIdx.x` 在 warp 内变化最快，所以它得顶 stride 为 1 的那一维，也就是行主序的列。顶到行索引上，一条指令的 32 个地址就散到 32 条 cache line，每条只取走一个 float。

- 关键细节（只记"之前不知道"或"和直觉相反"的点）：
  1. **先确认形状**：A[M,K] × B[K,N] = C[M,N]。kernel 1/2 的形状完全一致，kernel 2 只改了 blockDim 和线程→(行,列) 的映射。验证方法：把每个访问拆成 row*stride+col，stride 必须等于该矩阵的列数——`A[x*K+i]`（stride=K）、`B[i*N+y]`、`C[x*N+y]`（stride=N），三处互证。
  2. **x 是行、y 是列，`i` 只在行内滑动**：x 的上界由 gridDim 给出（`CEIL_DIV(M,32)*32`，靠 `x<M` 裁掉余数）；循环 K 次是内积长度，与 M 无关。`A[x*K+i]` 里 `x*K` 是行首偏移、`i` 是行内偏移，永远不会越到别的行。
  3. **合并与否只看单条访存指令内 32 个 lane 的地址，不看线程"整体"访问了哪些地址**：warp 按连续 `threadId` 切分，`threadIdx.x` 是变化最快的维度，所以必须让 `threadIdx.x` 去驱动 stride=1 的那一维（行主序的列）。kernel 1 里 `threadIdx.x` 驱动的是 x（行）→ 一条指令的 32 个地址相邻差 `K*4` 字节 → 32 次请求；kernel 2 里 `threadIdx.x` 驱动 cCol（列）→ 同一条指令的 32 个地址相邻差 4 字节 → 1 次 128B 事务。注意 kernel 1 里 `A[x*K+i]` 随 `i` 循环跑满 K 次，整个 warp *累计*读到的地址其实是连续的，但那是 K 条指令、每条内部跨行，照样不能合并。三种写法（换公式 / 换 blockDim 为 1D / 保持 2D block 但对调 x、y 在矩阵下标里的位置）等价。
  4. **SASS 不变**：合并是运行时由硬件完成的（要求地址对齐，编译期拿不到指针值，无法静态推断），所以 kernel 1→2 吞吐从 15GB/s 涨到 110GB/s 而汇编一个字节没变。另外 32 个 lane 之间不要求按 lane 顺序对应连续地址，落在同一段里就行。
  5. **原文陷阱**：正文散文把 `blockIdx.x` 说成对应 `CEIL_DIV(N,32)`，与 launch 的 `dim3 gridDim(CEIL_DIV(M,32), CEIL_DIV(N,32))` 顺序相反。以 launch 实参和下标表达式为准。

## 我没看懂的地方

- [x] Q1：`const uint x = blockIdx.x*blockDim.x + threadIdx.x; const uint y = ...threadIdx.y;` 算出来的就不能合并访存，为什么换成 `threadIdx.x / BLOCKSIZE` 和 `% BLOCKSIZE` 就能？
  - **答**：这两行不是两种算法，是同一个 32×32 tile 的双射，只是线程→(行,列) 的映射转置了。判据只有一条：看**同一条访存指令**下 32 个 lane 各自的地址，是不是落在同一段连续且对齐的区间里。
    - 旧写法（blockDim=(32,32)）：warp 内 `threadIdx.x` 从 0 到 31、`threadIdx.y` 恒定 → **x 变 y 不变** → warp 竖切 tile 的一整列 → 相邻 lane 地址差 `K*4`（K=4092 时 16368B）→ 32 条不同 cache line。
    - 新写法（blockDim=1024）：`threadIdx.x/32` 在 warp 内恒为 0 → 决定 x（行）；`threadIdx.x%32` 恰好等于 lane id → 决定 y（列）→ warp 横切 tile 的一整行 → 相邻 lane 差 4B → 一次 128B 事务。
    - 不必改成 1D block，保持 `blockDim=(32,32)` 把 x/y 在矩阵下标里对调即可。
  - 记法：**让 `threadIdx.x` 去乘那个 stride=1 的维度。** 作者从 kernel 3 起直接写成 `threadCol = threadIdx.x % BLOCK_SIZE`，注释就是 "Make the threadCol (=threadIdx.x) the consecutive index to allow global memory access coalescing"。
